# Phase 2 Plan 1: Local-First Product and Inventory Foundation

## Objective

Deliver the first production-backed inventory workflow in the existing React/Vite client while preserving the current root page as the client-reviewed prototype. Product and stock operations must commit locally, remain usable offline, and queue safe Supabase synchronization for when the device is online.

## Decisions

- Keep the root `index.html` prototype unchanged during this slice; the Vite client becomes the production implementation path.
- Give the production client a versioned Dexie schema/database separate from the legacy `ClothesManiaDB` snapshot to prevent cross-frontend overwrites.
- Keep Supabase configuration public-only (`URL` and anon/publishable key); server-side row-level policies protect remote records. No secret key belongs in browser code.
- Inventory quantities change only through stock-movement records. Every product/stock mutation and its outbox event commit in one local transaction.
- Migration is an explicit backup-and-preview operation. Retain every existing record; classify seeded prototype records so financial summaries can exclude them by default.
- No multi-device concurrent-edit behavior is introduced; sync is a single-device outbox push with stable IDs and idempotent retries.

## Tasks

1. Add a new production Dexie database with versioned product, stock-movement, outbox, metadata, and migration tables. Include transactional product creation/edit and stock-in APIs; surface persistence failures to callers.
2. Add a Supabase initial schema and row-level security policies for authenticated business members, stable client-generated IDs, and idempotent stock/outbox operations. Add no credentials or real project identifiers.
3. Add an online sync runner that drains local outbox events only after local commit, retries safely, exposes pending/error/last-success state, and is a no-op when credentials or connectivity are absent.
4. Replace only the React placeholder dashboard with a production Products/Inventory screen that uses the local repository, validates unique SKUs and stock values, shows sync state, and keeps core actions available offline.
5. Add migration preview/backup handling for legacy browser records without automatically treating sample orders as business sales. All records remain recoverable and are tagged by source.
6. Add focused automated tests for schema initialization, atomic stock movement/outbox writes, SKU/quantity validation, migration classification, and idempotent sync behavior.

## Verification

- Run the focused local DB and sync tests, then `npm run build` from `client/`.
- Verify local product/stock updates succeed with `navigator.onLine === false` and do not call Supabase.
- Verify a simulated retry of the same outbox event cannot apply the stock movement twice.
- Verify sample flags survive migration and production totals exclude sample-only transactions.
- Do not attempt a real Supabase connection or Vercel deploy until the owner supplies a project URL/anon key and the schema has been reviewed/applied.

## Risks / open items

- Supabase project credentials and production redirect domains are not yet configured.
- Offline authentication must retain a previously authorized local session; secure device-level protection and recovery behavior need validation before deployment.
- This slice establishes the shared local-first pattern; orders, payments, reporting, exports, cancellation/refunds, and final deployment remain subsequent phases.
